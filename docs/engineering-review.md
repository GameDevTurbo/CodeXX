# 工程优化分析与验收（2026-10-22）

## 结论

用户入口、开发源码、部署数据、发布产物应分开。普通使用者不应分辨一堆安装脚本；开发者与本机 AI 则需要稳定 CLI 和明确的失败语义，而不是只能操作 GUI。

## 已落地

| 问题 | 处理 | 用户收益 |
|---|---|---|
| 根目录实现和准备脚本混杂 | 稳定入口保留；客户端实现进 cliproxy_client，服务端实现进 server_app；历史脚本归档 | 找入口更容易，旧快捷方式仍可兼容 |
| 两仓库各维护一份客户端 | Server 停止构建旧 Client，只链接独立客户端 | 避免不同设备拿到不同修复版本 |
| Mac ZIP 仍通过 Python 源码启动 | Mac 改 App 发布，arm64/x64 独立 CI；启动器优先 App | 发布版不再要求 Python |
| 全局 pip/重复安装/失败继续 | 源码 .venv、依赖指纹、安装后检测、非零失败与日志 | 不污染全局环境，错误可以定位 |
| Server 写入临时解包目录 | 新版使用持久数据目录；旧配置原位兼容 | 更新程序不丢账号、Key 和配置 |
| 重复 Setup 重置 Key | 幂等初始化；既有和不完整配置均不盲目覆盖 | 不再让已连接客户端突然失效 |
| 部署命令失败仍显示成功 | 按子进程退出码决定成功回调 | 失败不再伪装成“已部署” |
| GUI 显示/日志输出管理凭据 | 界面遮蔽、日志不打印，连接导出排除管理密码 | 降低截图与诊断泄露风险 |
| AI 难以操作或判断状态 | 两端 AI_START.md；Server --doctor/--init/--export-profile；Client 保留路由核验 | 可先只读、再按授权推进 |
| 打包混入私密数据/链接失效 | 白名单包、完整文档、架构清单、SHA256与解压运行检查 | 交付给别人的是可用成品，不是开发目录 |

## Windows 本轮自测

58 项隔离行为检查通过：客户端配置/认证字段 11、路由读取 12、路由 UI 回调 5、进程隔离分支 5、打包监护恢复 1、Server 初始化/诊断/导出 16、两端发布包与启动参数 8。

另外完成 Python 编译、Shell/PowerShell 语法、源码启动参数传递、UTF-8 无 BOM 与密钥模式检查。发布包在包含中文和空格的临时目录中、移除 PATH 中 Python 的环境下运行 CLI；不使用真实配置进行循环开关测试。

本机 Server 只读诊断确认旧配置可识别，Docker 引擎和 Compose 可用；未重建、重启、升级线上容器，也未自动发送付费生成请求。

## 尚未完成或不能据此证明

- macOS 的 Finder、GUI、Tailscale 网络扩展、托盘和 Docker 网络需 Mac 实机验收；本轮只有静态与模拟路径检查。
- Mac 签名/公证、Windows 代码签名、自动更新尚未接入。
- 新 CI 已写入仓库，但未推送或运行 GitHub Actions；Windows 本机构建不等于 Mac 发布成功。
- 本轮最后的桌面启动被系统拒绝访问，故新客户端尚未恢复常驻；文件已升级，旧配置已正常恢复，待桌面权限恢复后再验收一次 GUI。
- --doctor 检查配置与服务，不查询上游具体账号或剩余额度。
- latest 镜像仍适合试用而非严格生产版本控制；正式部署前需要制定固定 tag/digest 和回滚策略。

## Server 长期运行复核

- 新初始化的 Compose 设置 `unless-stopped`、优雅停止、CPU/内存/进程数上限和 Docker 日志轮转。
- `--harden-runtime` 可对已有 Compose 补齐缺失项，保留用户已设置的值，不自动重启服务。
- 资源阈值是保守默认值，正式长期运行前仍应结合上游模型、并发量和主机内存监控调整。
